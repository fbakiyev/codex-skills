## Работа с проектом и проверка результата (`core`)

Навыков: 5. [Роли](../agents/core/) · [Рабочие процессы](../workflows/core/) · [Сценарии проверки](../evals/sample-tasks/core/)

| Навык | Когда применять |
| --- | --- |
| [artifact-handoff](../skills/core/artifact-handoff/SKILL.md) | Подготовка сводки, по которой другой человек сможет продолжить работу, когда требуется передача или сохраняемая запись о завершении. Зафиксируйте проверенное состояние, решения, препятствия и следующие действия; обычное завершение задачи само по себе не требует отдельного документа. |
| [context-memory](../skills/core/context-memory/SKILL.md) | Сохранение краткого контекста проекта по запросу пользователя или при реальной необходимости передать работу. Записывайте источники, текущее состояние, решения и незавершённые действия в выбранное место с подходящей видимостью; не применяйте к каждой завершённой задаче. |
| [project-discovery](../skills/core/project-discovery/SKILL.md) | Изучение незнакомого репозитория или технического проекта перед реализацией: точки входа, команды проверки, границы выполнения и существенные ограничения. Применяйте при нехватке контекста проекта, а не как обязательный этап самостоятельной офисной задачи. |
| [skill-evolution-loop](../skills/core/skill-evolution-loop/SKILL.md) | Улучшение библиотеки навыков по запросу пользователя или когда согласованная проверка выявила повторяющуюся проблему инструкций. Применяйте для целенаправленных изменений навыков; ошибка обычной задачи сама по себе не разрешает менять общие инструкции. |
| [technical-review](../skills/core/technical-review/SKILL.md) | Проверка предлагаемого технического изменения или документации на конкретные дефекты, регрессии, пробелы проверки и эксплуатационные риски. Применяйте по запросу на ревью или для существенного изменения, требующего независимой оценки; не вводите формальное согласование каждой мелкой правки. |

## Требования и управление поставкой (`agile-delivery`)

Покажите изменения со времени предыдущего обновления, подтверждения и препятствия; на обычный вопрос о статусе отвечайте прямо, без создания документов спринта. |
| [backlog-management](../skills/agile-delivery/backlog-management/SKILL.md) | Создание или уточнение запрошенного бэклога либо структуры работ с критериями приёмки, зависимостями и приоритетами. | [linear-export](../skills/agile-delivery/linear-export/SKILL.md) | Подготовка проверяемого сопоставления локального бэклога с конкретной командой Linear: нерешённые поля и выбор создания или обновления пунктов. Применяйте для подготовки экспорта или явно запрошенной синхронизации, а не обычного планирования бэклога. |
| [requirements-analysis](../skills/agile-delivery/requirements-analysis/SKILL.md) | Уточнение неоднозначной функции или бизнес-изменения до проверяемых требований, границ и нерешённых вопросов. Применяйте перед проектированием решения, когда нужное поведение неясно; не требуйте отдельного исследования для уже определённой небольшой правки. |
| [sprint-planning](../skills/agile-delivery/sprint-planning/SKILL.md) | Планирование запрошенного спринта в действующем процессе с учётом цели, бэклога, зависимостей и доступной ёмкости команды. Применяйте для согласования ограниченного объёма спринта, а не как процесс по умолчанию для мелких изменений или инцидентов. |
| [sprint-review-retro](../skills/agile-delivery/sprint-review-retro/SKILL.md) | Проведение запрошенного обзора спринта или поставки и ретроспективы по исходной цели, подтверждениям приёмки и наблюдаемым проблемам процесса. Не запускайте ретроспективу и не меняйте общие навыки после каждой завершённой задачи. |
| [system-analysis](../skills/agile-delivery/system-analysis/SKILL.md) | Преобразование требований к функции или интеграции в границы систем, переходы состояний, контракты данных и поведение при сбоях. Применяйте, когда реализации нужна модель поведения; выяснение бизнес-цели относится к анализу требований. |

Использовать для изменения жизненного цикла ресурсов или конфигурации; поставку под управлением контроллера сверки состояния направлять в gitops-delivery. |

Использовать для проектирования и проверки мониторинга, а не простого чтения дашборда во время диагностики. |

## Разработка программного обеспечения (`software-engineering`)

Навыков: 6. [Роли](../agents/engineering/) · [Рабочие процессы](../workflows/engineering/) · [Сценарии проверки](../evals/sample-tasks/engineering/)

| Навык | Когда применять |
| --- | --- |
| [api-design](../skills/software-engineering/api-design/SKILL.md) | Определить или развить контракт API, события, webhook или пакетного интерфейса, включая наблюдаемую совместимость, повторные запросы и ошибки. Применять для решений об интерфейсе; реализация относится к backend-разработке, а исполняемые проверки контракта — к тестированию API. |
| [backend-engineering](../skills/software-engineering/backend-engineering/SKILL.md) | Реализовать или переработать серверное поведение в сервисах, фоновых заданиях, интеграциях или предметной логике. Применять для изменений кода и поведения при сбоях; решения по контракту относятся к проектированию API, запрос только на проверку — к review кода. |
| [code-review](../skills/software-engineering/code-review/SKILL.md) | Проверить предлагаемое изменение кода на конкретные дефекты, регрессии, нарушения совместимости и существенные пробелы проверки. Применять для замечаний по коду, а не реализации функции, проектирования стратегии тестирования или оптимизации системы без измерений. |
| [database-engineering](../skills/software-engineering/database-engineering/SKILL.md) | Изменить или оценить схемы, запросы, индексы, транзакции и миграции базы данных с учётом совместимости данных и приложений. Применять для изменений базы; выполнение восстановления относится к эксплуатационным сценариям, а поиск более широкой причины замедления — к анализу производительности. |
| [frontend-engineering](../skills/software-engineering/frontend-engineering/SKILL.md) | Создать или изменить интерактивный frontend-сценарий, компонент или переход клиентского состояния, включая доступность и адаптивность. Применять для реализации продукта; браузерные регрессионные тесты относятся к E2E-тестированию frontend, а запрос только на проверку — к review кода. |
| [performance-engineering](../skills/software-engineering/performance-engineering/SKILL.md) | Исследовать измеренную проблему производительности и оценить прицельную оптимизацию кода, запросов, отрисовки или использования ресурсов. Применять для поиска узкого места и изменений; проектирование нагрузки и оценка измерений ёмкости или регрессий относятся к тестированию производительности. |
