# Установка, инструменты и выполнение задач

Это руководство относится ко всем девяти пакетам. Выбор области и примеры работы — в [README](../README.md), полный список — в [каталоге](catalog.md).

## Подготовка

Локальные инструменты требуют Python 3.9 или новее и PyYAML из `requirements-dev.txt`. Команды ниже рассчитаны на macOS/Linux и выполняются из корня клонированного репозитория. Они не используют API модели и не требуют учётных данных облачных сервисов.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Навык можно установить вручную, скопировав всю его папку в `.agents/skills/<name>/` целевого проекта либо `~/.agents/skills/<name>/` для личного использования. Python нужен локальным утилитам библиотеки; необходимые для самой задачи средства определяются проектом. [Локальные пути Codex](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills).

## Поиск и выбор

```bash
.venv/bin/python scripts/manage_skills.py list
.venv/bin/python scripts/manage_skills.py list --pack xops-platform --pack security
.venv/bin/python scripts/manage_skills.py list --query RAG
.venv/bin/python scripts/manage_skills.py list --pack data-platform --json
.venv/bin/python scripts/manage_skills.py show data-engineering
```

`list` фильтрует каталог по области и тексту. `show` показывает описание, путь, роли с явной ссылкой на навык и процессы/сценарии его пакета. Последние относятся к пакету и не обязательно нужны каждому запросу. JSON удобен для собственных средств поиска и автоматизации.

Выбирайте навыки по результату и границе работы. Например, `api-design` задаёт контракт, `backend-engineering` реализует поведение, а `api-testing` проверяет работающую границу. Для запроса только на ревью достаточно `code-review`; установка большого набора не должна навязывать полный цикл разработки.

## Установка выбранного набора

Назначение всегда задаётся явно через `--dest`. Замените `/path/to/project` на свою рабочую папку:

```bash
.venv/bin/python scripts/manage_skills.py install \
  --pack software-engineering --pack qa-aqa \
  --dest /path/to/project/.agents/skills --dry-run
```

`--dry-run` показывает план без записи. Та же команда без этого флага копирует выбранные папки. Вариант с отдельными навыками:

```bash
.venv/bin/python scripts/manage_skills.py install \
  --skill data-engineering --skill data-quality \
  --dest /path/to/project/.agents/skills
```

`--skill` и `--pack` не смешиваются в одной команде; каждый флаг можно повторить. В назначении появятся папки вида `data-engineering/SKILL.md` со всем необходимым вложенным содержимым. Общий `AGENTS.md`, роли и шаблоны репозитория туда не копируются.

Перед первой записью проверяется весь выбранный набор. Полностью совпадающая установленная папка пропускается, отличающаяся вызывает ошибку. Символические ссылки в исходных навыках или назначении не поддерживаются. Для ошибок выбора и конфликтов возвращается код 2, для успешного выполнения — 0. Установка не меняет настройки модели и не запускает приложение.

Установка всего набора не является атомарной операцией. После аварийного завершения процесса или ОС проверьте появившиеся папки: повторная команда пропустит полные совпадающие копии, а неполную копию обозначит как конфликт.

Шаблоны из `templates/` необязательны. Чтобы использовать их вместе с установленным навыком, оставьте копию репозитория доступной и укажите её расположение в задаче.

## Инструменты для предметной работы

Средства в этой таблице предоставляются проектом или подключённой средой. Это ориентир по зависимостям, а не список программ, которые обязательно установить все сразу.

| Область | Достаточный контекст | Средства выполнения по задаче | Что проверять в результате |
| --- | --- | --- | --- |
| Разработка | Исходники, контракт, версии зависимостей, команды проекта | Git, сборка, тестовый раннер, средства работы с БД или браузером | Изменённый путь, совместимость, состояние после сбоя и регрессии |
| Платформа и эксплуатация | Желаемая и текущая конфигурация, окно инцидента, ограничения среды | Используемые Terraform/OpenTofu, Kubernetes или облачные CLI, журналы и метрики | Фактическую ревизию и эффект, а для восстановления — данные и работоспособность сервиса |
| Данные | Схема, смысл строки, ключи, версии и контрольные итоги | SQL, используемые dbt/Spark/оркестратор либо локальная обработка файлов | Полноту, повторную обработку, поздние исправления, соединения и итоговые значения |
| ML и RAG | Версии данных, время доступности признаков, эталоны, трассы поиска и генерации | Средства ML проекта, хранилище признаков, retrieval-система или модельный клиент | Утечки, сопоставимость, ошибки, права на источники и подтверждение цитат |
| QA | Критерии, известный сбой, тестовые данные и среда | Тестовый framework проекта, API-клиент, браузерная или нагрузочная инфраструктура | Независимый ожидаемый результат, изоляцию состояния и воспроизводимость |
| Безопасность | Границы доверия, код, конфигурация, состав реально поставленных компонентов | Анализ кода и конфигурации, применимые сканеры, сведения о правах и уязвимостях | Достижимость проблемы, последствия, применимость исправления и оставшиеся неизвестные |
| Требования и поставка | Источники требований, принятые решения, зависимости и ёмкость | Файлы и документы; Linear или другой трекер только для запрошенной синхронизации | Условия и исключения, критерии приёмки, владельцев и поля без выдуманных значений |
| Работа с проектом | Рабочая папка, локальные правила и цель | Поиск по файлам, Git и команды проверки проекта | Подтверждённую карту компонентов, результат ревью и нужные сведения для продолжения |
| Офисная работа | Исходные документы, таблицы, заметки, аудитория и формат | Работа с DOCX/XLSX/PPTX/PDF, рендер, подключённые документы и почта по запросу | Содержание, условия, расчёты, оформление и фактически созданный файл |

Наличие навыка не означает наличие перечисленных средств или доступа. Сначала выясняйте фактические интерфейсы и версии. Если проверка или экспорт недоступны, подготовьте возможный результат и назовите конкретную границу проверки. Успешное чтение конфигурации не доказывает успешный запуск сервиса.

Пользовательский запрос и правила проекта определяют разрешённые действия. Запрос на диагностику или подготовку плана не превращается автоматически в изменение инфраструктуры; уже согласованную работу не нужно повторно согласовывать из-за формулировок навыка.

## Проверка поведения

Экспортер готовит материалы для прогона; он не обращается к модели и не оценивает ответ автоматически.

```bash
.venv/bin/python scripts/prepare_eval.py list
.venv/bin/python scripts/prepare_eval.py list --pack ml-mlops --json
.venv/bin/python scripts/prepare_eval.py prepare data-platform/pipeline-delivery \
  --output /tmp/pipeline-eval
```

Назначение должно быть новой папкой. Результаты имеют разное назначение:

| Файл | Кому и зачем |
| --- | --- |
| `task.md` | Проверяемой модели: выбранные инструкции, запрос и исходные данные первого шага |
| `criteria.md` | Проверяющему: критерии качества и признаки ошибок |
| `manifest.json` | Организатору: версия, источники, контрольные суммы, условия и порядок шагов |
| `steps/02/task.md` и далее, если есть | Модели только после ответа на предыдущий шаг |

Не передавайте проверяемой модели весь каталог экспорта: так она получит критерии и будущие условия. Для сравнения моделей используйте отдельные одинаково подготовленные задачи и одинаковые доступные инструменты. Сохраните ответы, фактически выбранную модель и настройки, условия выполнения, время и ошибки. Проверяющий сопоставляет результат с критериями, а не только с формулировкой образца.

У некоторых примеров требуется заранее подготовленный проект, тестовая среда или материал. Соблюдайте указанный режим и условия в manifest; экспорт таких заданий не создаёт среду и не разрешает произвольные внешние действия. Многошаговый пример может проверять, что новое разрешение учитывается лишь после следующего запроса. Имитация отправки сообщения используется только в локальном тестовом окружении без сети.

Сценарии покрывают инженерные и офисные ошибки: совместимость API, дубли и поздние данные, утечки в ML, права RAG, неполное восстановление, нагрузочные измерения, условия документов и расчёты. Текстовый ответ не подтверждает развёртывание, нагрузочный тест или рендер файла. Для этих выводов нужен соответствующий фактический запуск.

## Обновление

Установленные папки являются копиями. Обновление исходного репозитория само по себе их не изменяет. Сравните версии и сохраните свои правки; утилита установки намеренно не перезаписывает отличающуюся папку. После проверки замены обновите её вручную целиком, не оставляя старые вспомогательные файлы. Не удаляйте старую копию до подготовки и проверки новой.

При переходе с версии до `1.1.0` изменились три пути внутри `skills/`; значения `name` сохранены:

| Прежняя папка | Текущая папка |
| --- | --- |
| `agile-delivery/review-retro` | `agile-delivery/sprint-review-retro` |
| `xops-platform/platform-design` | `xops-platform/xops-platform-design` |
| `data-platform/orchestration` | `data-platform/data-orchestration` |

При изменении состава библиотеки пересоберите каталог и выполните проверки:

```bash
.venv/bin/python scripts/inventory.py --markdown > docs/catalog.md
.venv/bin/python scripts/validate_repo.py
.venv/bin/python -m unittest discover -s tests -v
```

При изменении исходного сценария в `evals/sample-tasks/` пересмотрите соответствующую запись в `evals/cases.yaml`: какие фрагменты получает модель, какие остаются проверяющему и когда выдаётся следующий шаг. Затем обновите `source_sha256` по содержимому исходного файла. Экспортер отклоняет изменившийся источник, пропущенные фрагменты и пересечения задания с критериями; одной замены контрольной суммы без проверки разделения недостаточно.

Файл `docs/catalog.md` строится из фактических путей и описаний, поэтому новые навыки не должны оставаться невидимыми в документации. Валидация структуры не заменяет предметную проверку изменённого поведения.
