# Проверка повторов в API резерваций

## Границы выполнения

Примени `api-design` и `code-review` к исходным данным. Для предлагаемой реализации можно использовать `backend-engineering` или `database-engineering`. Упражнение выполняется только ответом: не редактируй репозиторий, не запускай миграции и не обращайся к внешним сервисам.

## Запрос

Проверь предлагаемую поддержку повторов в endpoint резерваций. Найди достижимые дефекты, предложи ограниченное исправление, сохраняющее клиентский контракт, и конкретные локальные регрессионные случаи. Отличай ошибку этого предложения от проблемы, уже предотвращённой в контрпримере.

## Исходные данные

Существующий контракт и новые требования:

```text
Создание возвращает HTTP 201 с {"reservation_id": "..."}.
Существующий клиент принимает только 201 и читает body["reservation_id"].
Запросы принадлежат аутентифицированной учётной записи; account берётся из аутентификации.
Новое требование: одинаковые повторы в одной учётной записи возвращают ту же резервацию.
Тот же ключ с другими данными в этой учётной записи должен вернуть 409 без изменения остатка.
Разные учётные записи могут использовать тот же ключ для независимых запросов.
```

Предлагаемая реализация в псевдокоде:

```python
def reserve(account, key, body, store):
    previous = store.get_by_key(key)
    if previous is not None:
        return previous
    reservation_id = store.reserve_stock(account, body["sku"], body["quantity"])
    response = (200, {"id": reservation_id})
    store.remember(key, response)
    return response
```

`reserve_stock` атомарно проверяет доступный остаток, уменьшает его и создаёт резервацию с уникальным идентификатором. `remember` — отдельная устойчивая запись без общей транзакции или ограничения уникальности пары account/key. Начальный остаток `SKU-1` равен 2; каждый запрос ниже требует 1. Внешнего провайдера нет. Два запроса могут прочитать отсутствие ключа до того, как любой из них зарезервирует остаток. Процесс может остановиться после фиксации `reserve_stock`, но до `remember`.

## Ожидаемое поведение

- Изменённый статус и поле названы нарушением контракта предоставленного клиента, а не неопределённым предпочтением по стилю.
- Выявлены коллизия ключа между учётными записями и возврат старого результата для того же ключа с другими данными без проверки.
- Приведены конкретное чередование дубликатов и случай сбоя с повтором, создающие две резервации вопреки требуемому поведению повторов.
- Предложены ключ в области учётной записи и проверка идентичности входных данных, а резервация и запись повтора защищены подходящей устойчивой атомарной границей. Ответ сохраняет существующий клиентский контракт.
- Проверяются одинаковый повтор, одновременный дубликат, конфликтующие данные и потерянное подтверждение по идентификатору резервации и числу эффектов или остатку, а не только по успешным HTTP-ответам.
- Указано, что атомарное локальное решение опирается на заданную границу одного хранилища; перенос резервации к внешнему провайдеру потребует дополнительного контракта идемпотентности или сверки.

## Контрпример

Другая реализация уже использует транзакцию с резервацией и уникальной записью `(account, key)`, содержащей идентичность входных данных. Дубликат читает зафиксированный результат; конфликтующие данные возвращают 409. Ответ имеет статус 201, поле `reservation_id` и дополнительное необязательное поле `note`. Предоставленный существующий клиент игнорирует неизвестные поля.

Не повторяй исходные замечания к этой реализации только потому, что она добавляет поле ответа, содержит предварительную проверку или использует повторы. Называй оставшийся достижимый дефект только при наличии оснований в исходных данных.

## Критерии провала

- Утверждение, что одна локальная блокировка процесса или кеш после выполнения эффекта обеспечивает устойчивую безопасность повторов.
- Пропущено конкретное нарушение клиентского контракта, ключи остаются глобальными или проверяются только коды возврата.
- Утверждение, что остаток может стать отрицательным, хотя в условии `reserve_stock` явно атомарно проверяет остаток.
- Заявление о выполнении реальных тестов, миграций или изменений сервиса в упражнении, ограниченном ответом.
