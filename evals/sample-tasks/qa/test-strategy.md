# Стратегия регрессионной проверки поиска и сохранения

## Границы выполнения

Примени `qa-strategy`, `test-automation` и относящиеся к задаче части `frontend-e2e-testing`. Используй только предоставленные данные. Верни проект тестов и исправленные проверки в псевдокоде; не открывай настоящее приложение и не меняй общий CI.

## Запрос

Замени ненадёжный план небольшим набором проверок, выявляющих реальные дефекты. Объясни независимый критерий правильности каждого теста, самый низкий подходящий уровень и изоляцию при параллельных запусках. Включи содержательные проверки клавиатуры и имени для изменённого элемента сохранения.

## Исходные данные

Поведение продукта:

```text
Поиск должен показывать результаты для последнего ввода.
Сохранение черновика должно сохранять его заголовок и удерживать его после перезагрузки.
Новый элемент сохранения показывает только значок дискеты и не имеет имени для средств доступности.
formatPercent(n, d) возвращает round(100 * n / d, 1) с добавленным в конце "%".
```

Реализация и текущие тесты в псевдокоде:

```python
on_input = lambda query: fetch_results(query).then(render_results)

test_percent:
    expected = formatPercent(1, 2)
    assert label_for_ratio(1, 2) == expected

test_save:
    use_account("shared-demo")
    open_existing_draft("Common draft")
    click(".toolbar button:nth-child(2)")
    sleep(1)
    assert page_contains("Saved")
    delete_all_drafts("shared-demo")
```

Управляемые входные данные:

```text
Запрос "printer" отправляется первым и возвращает ["Printer"] последним.
Запрос "paper" отправляется вторым и возвращает ["Paper"] первым.
На странице уже может быть постороннее сообщение "Saved" от предыдущего действия.
Два теста сейчас одновременно меняют одну учётную запись и один черновик.
Требование продукта для процентов: 1/2 -> "50.0%" и 1/4 -> "25.0%".
```

## Ожидаемое поведение

- Для процентов используются независимые фиксированные значения на модульном или компонентном уровне вместо вызова той же функции форматирования для ожидаемого ответа.
- Порядок завершения двух запросов управляется, и проверяется, что итоговые видимые результаты по-прежнему соответствуют `paper`. Увеличенная пауза не предлагается как исправление.
- У каждого теста сохранения своё состояние, и очистка ограничена им; новый браузер сам по себе не считается изоляцией backend.
- Для сохранения используется устойчивый осмысленный локатор, а отсутствие имени для средств доступности названо поведением продукта, которое нужно исправить. Безымянный значок не закрепляется хрупким селектором.
- Определена ограниченная по времени проверка завершения сохранения нового черновика и последующая проверка его заголовка после перезагрузки; постороннее старое уведомление не удовлетворяет критерию правильности.
- Включены достижимость изменённого элемента с клавиатуры и его активация. Скриншот или автоматическая проверка доступности не описываются как доказательство всего взаимодействия.
- Исчерпывающие случаи форматирования остаются ниже E2E; выбран только нужный браузерный путь. Фактическое выполнение обозначено как выходящее за рамки упражнения.

## Контрпример

Порядок элементов панели в DOM меняется, но у элемента сохранения остаются уникальное имя для средств доступности и прежнее поведение. Правильные тесты должны продолжать проходить. Другой набор создаёт независимые черновики в изолированных тестовых учётных записях и удаляет только эти черновики; не требуй последовательного выполнения лишь потому, что сервер общий.

## Критерии провала

- Рекомендация глобальной очистки, произвольных пауз, повторов до зелёного результата или отключения неуспешной проверки без дальнейшей работы.
- Ожидаемый результат вычисляется тем же форматтером, проверяется только старое уведомление или все случаи заменены браузерными E2E-тестами.
- Утверждение, что одно имя для средств доступности доказывает поведение клавиатурного фокуса и взаимодействие, либо заявление об успехе невыполненных тестов.
